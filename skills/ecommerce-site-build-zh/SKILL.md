# 独立站 / 跨境电商网站：新建与改版（中文版）

把一个独立站从需求做到上线，或者把老站整体 / 局部改版。整个流程围绕 **5 道确认闸门（Gate）** 设计，闸门之间才是"干活"。

这套流程来自一次真实的 Shopify 独立站改版（几百个产品、换主题、产品页重写、博主测评区）。最大的教训只有一条：**每一步做完先给用户看、等用户明确说"确认"，再往下走。** 那次试点产品做完没等确认就铺到了全部产品，用户原话是 "confirm with me once you finish the pilot product"。

本 Skill 是面向中文团队的版本。英文团队请使用英文版 `ecommerce-site-build`。

```
G0 需求澄清 → G1 素材就绪 → G2 HTML 方向稿选定 → G3 样板页确认 → G4 定稿 → 批量铺开 → 上线后验收
```

每道闸门都要用户在对话里**明确同意**（用选择题提问最省事）。没拿到确认就停下等，不要"先做着"。用户不在线时，把准备工作做完、把需要他决定的事写清楚，然后停在闸门前。

## 工具：按能力找工具，不写死工具名

本 Skill 可以在不同的 Agent 里运行（Claude.ai、Claude Code、ChatGPT、Codex 等），每个 Agent 的工具名不一样。下面写的都是**能力**，用当前环境里能提供这个能力的工具；都没有就走兜底方案。

| 能力 | 用什么 | 没有时的兜底 |
|---|---|---|
| 向用户提问 | 结构化选择题工具（Claude 里是 AskUserQuestion） | 在对话里列出编号选项让用户回复 |
| 发布可分享的页面 | Artifact / Canvas 等能生成网页链接的工具（有 Design 类型优先用） | 交付自包含的 `.html` 文件，让用户本地打开或自己部署 |
| 店铺后台 | Shopify 连接器 / Admin GraphQL；其他平台的 API 或 MCP | 用浏览器操作（用户自己登录）；或导出 CSV 让用户导入 |
| 部署静态站 | Vercel / Netlify / GitHub 相关工具 | 输出代码包，让用户自己部署 |
| 网页浏览与截图 | 浏览器自动化工具 | 让用户打开页面截图或粘贴内容 |
| 连接器推荐 | 能搜索或推荐 MCP / 连接器的工具 | 明确告诉用户要装什么、需要哪些权限 |
| 进度记录 | 项目（Project）文档、记忆、仓库里的文件 | 在对话里输出进度文档全文，让用户自己保存 |

缺某个能力时：说清楚缺什么、能用什么兜底，让用户选：**安装** / **用兜底方案** / **换一个方案**。不要卡住不说话。

## 贯穿全程的原则

1. **不碰线上。** 一切改动在草稿 / 副本 / 预览环境里做（Shopify 复制一个未发布主题，HTML 用 staging 部署）。发布由用户自己点。
2. **先备份，后写入，写完读回来核对。** 每次批量写之前导出原数据（JSON / CSV），写完从系统里重新读出来和目标逐条比对，不能只看接口返回"成功"。
3. **不编造。** 评价、认证、数字、媒体背书、创始人故事，只用用户给的或能查到出处的。查不到就标【待用户补充】。电商页面上的假评价、假认证是合规问题，不只是质量问题。
4. **范围外的问题只标记不修改。** 过程中会发现很多别的问题（事实矛盾、错别字、数据不一致），列进"待确认清单"交给用户，不顺手改。
5. **统一前缀。** 给自己创建的东西（主题名、section、metafield、自动化）加统一前缀，方便用户一眼分辨哪些是 Agent 做的。
6. **记录决策。** 维护一份进度文档：每道闸门的选择、日期、备份位置、待办。有项目（Project）就写进项目里，会话中断后下一个会话能接着做。

## G0 需求澄清

对话、项目文档或记忆里已经有答案的就不要再问，直接写进需求摘要让用户核对。第一轮只问会改变路线的问题，一次问完（最多 4 题）：

1. **新站还是老站？** 全新建站 / 老站整体改版 / 老站只改部分页面（如只改产品页）
2. **用什么框架？** Shopify / 纯 HTML 静态站 / WordPress + WooCommerce / Shopline、Shoplazza 等 / 其他（Next.js 等）
3. **卖到哪里？** 目标市场、语言、币种（决定跨境模块：多币种、关税、物流、隐私法规）
4. **品类和规模？** 卖什么、大约多少 SKU、客单价区间

然后按路线收集信息（一次列清单让用户填，不用一题一题问）。

**新站要的信息**
- 品牌名、域名、一句话定位、目标客户是谁
- 3 个参考网站（喜欢它哪里）和 3 个直接竞品
- 产品资料：最好是一张表（标题、价格、规格 / 变体、库存、主图、描述、分类）
- 运营规则：包邮门槛、退换货政策、配送时效、支付方式、联系邮箱、公司主体
- 必须避开的词或说法（行业术语白名单 / 黑名单、合规禁区）

**老站要的信息**
- 网址和后台访问方式
- 哪些必须保持不变：导航、URL、结账流程、某些页面、自定义代码、已装的 app
- 现在的痛点（"看起来不高级"、"转化低"、"手机端乱"）和已有数据（GA4、转化率）
- **先做一次只读审计再动手**：主题 / 模板清单、app 嵌入和 app block 清单、追踪代码（GA4 / GTM / Meta / 像素来源，有没有重复计数）、自定义代码、SEO 设置（noindex、结构化数据）、坏掉的东西。审计结果按 🔴 严重 / 🟡 应改 / 🟢 小问题 列给用户。老站改版最容易丢的就是这些"看不见的东西"。

**按平台的准备工作**：Shopify 要先确认连接器和权限，并提前告诉用户哪些事 API 做不了、要他自己点；纯 HTML 要先定部署和购物车方案。详见 `references/platforms.md`。

**G0 出口：** 一段需求摘要（新 / 老、框架、市场、范围、不能动的东西、已知限制），用户确认无误。

## G1 素材就绪

开工前列一张素材清单，每项写清"有没有、链接在哪"。用户给链接（Google Drive、Dropbox、Figma、Shopify Files、现有网站）即可，不需要上传。

| 素材 | 必需？ | 说明 |
|---|---|---|
| Logo | 必需 | 最好 SVG；横版、方版、浅色 / 深色背景各一 |
| 品牌色 | 必需 | HEX 色值；没有就从 logo 或参考站提取后让用户确认 |
| 字体 | 必需 | 名称和授权来源（Google Fonts 最省事） |
| 品牌规范 / 参考站 | 推荐 | 有 brand guideline 就用，没有就用参考站截图 |
| 首屏主视觉 | 必需 | 横幅图或视频；视频要有备用封面图 |
| 产品图 | 必需 | 每个产品至少 3 张：白底主图、细节、尺寸感或场景图 |
| 产品文案 | 必需 | 老站可直接读现有数据 |
| 品牌故事 / 关于我们 | 推荐 | 创始人、时间线、产地、工艺；能附出处更好 |
| 评价来源 | 推荐 | 用哪个评价 app、有没有真实评价可引用 |
| 认证与资质 | 视品类 | 证书原件或编号，没有证据的认证不上页面 |
| 政策文本 | 必需 | 运费、退换货、隐私、条款；包邮门槛和联系邮箱要全站一致 |
| 社媒链接 | 推荐 | Instagram、YouTube、TikTok 等 |
| 博主 / KOL 内容 | 可选 | 视频链接、文章链接，用于产品页测评区 |
| 术语白名单 / 禁用词 | 视品类 | 行业标准、品牌用语习惯 |

规则：
- **不用全齐才开始。** 做方向稿的最低要求：logo、品牌色或参考站、1 张主视觉、1 个资料完整的产品。其余缺的标【占位】，在后续闸门前补上。
- **缺的素材不要编**，也不要用无关的图库图冒充产品图。可以用明显的占位块。
- **素材里的矛盾当场问清楚**（比如首页写"全球包邮"、公告栏写"满 $70 包邮"），这类不一致上线后最伤信任。

**G1 出口：** 素材清单（含链接和缺项）用户确认，最低开工素材到位。

## G2 HTML 方向稿

目的：用最低成本让用户在 2–3 个明显不同的方向里选一个，而不是在真实平台上反复改。

1. **老站先做诊断**：现状截图 + 问题清单（🔴🟡🟢），说明改版要解决什么。
2. **出站点结构图**：页面清单、每类页面用哪个模板、哪些页面共用模板。老站附"旧 → 新"对照，标出不变的部分。
3. **出 2–3 版 HTML 方向稿**，每版都是自包含的单文件 HTML，桌面和手机都能看：
   - 版本之间要真的不同，例如 A 克制高端（大留白、编辑感）、B 转化导向（信息密、信任元素前置）、C 叙事型（品牌故事和产地驱动）。
   - 用真实素材和真实产品（真 logo、真产品图、真文案），不用 lorem ipsum，否则用户没法判断。
   - 至少包含首页首屏到信任条，最好再加一个产品页首屏。
   - 发布成可分享的页面（Artifact 等），用户可以在手机上看、发给合伙人看；没有就交付 HTML 文件。
4. **附一张对比表**：每版的设计思路、适合什么、取舍。
5. 让用户选：A / B / C / 混合（说明要哪版的哪部分）。

**G2 出口：** 选定方向，并把它锁成**设计规范**：颜色（HEX）、字体和字号层级、间距、圆角、按钮样式、卡片样式。写进进度文档，后面所有页面都按这份规范来。

## G3 样板页

在真实平台上把选定方向做出来，但**每类模板只做一个样板**：
- 首页
- 1 个分类页
- 2–3 个产品页：一个畅销款、一个内容最复杂的（多规格 / 长描述）、一个边缘情况（没有评价、缺货、图片少）
- 1 个内容页（如 About）
- 购物车

Shopify：在复制出来的未发布主题里做，给预览链接（`?preview_theme_id=`）。HTML：部署到 staging 地址。

**交付样板前自己先验收**（批量铺开后的整体 QA 也用这张清单）：
- [ ] 桌面 1440px 和手机 390px 截图，没有横向溢出
- [ ] 无 Liquid / JS 报错；每页一个 H1
- [ ] 无障碍检查（axe，WCAG 2.1 AA）
- [ ] 追踪事件：一次浏览产品只触发一次 `page_view` 和一次 `view_item`
- [ ] 加购 → 购物车 → 结账跑通
- [ ] 已有 app（评价、会员、弹窗、筛选）都正常加载
- [ ] 边缘情况：没有评价时不显示 0 星；视频在被屏蔽或无法播放时有封面图兜底

给用户看：预览链接 + 关键截图 + 改了什么 + 待决定的问题。然后**停下来等反馈**，按反馈改，直到用户满意。

## G4 定稿

样板页改到满意后，单独做一次"定稿确认"，确认的不只是外观，还有铺开方案：
- 要改的模板和页面完整清单、数量
- 每类页面会应用什么，哪些保持不变
- 备份放在哪、出问题怎么回滚
- 需要用户自己做的事（发布主题、开 app 嵌入、粘贴像素代码等）
- 预计分几批、每批多少

用户明确说"开始铺开"后再进入下一步。

## 批量铺开

1. **备份**：导出所有会被改动的数据；Shopify 主题先复制一份。
2. **分批执行**：每批 20–50 个，每批记录改了哪些。
3. **逐条核对**：从系统里重新读出来和目标比对（导出后程序比对，不靠肉眼抽查），数量对得上才算完成。
4. **异常清单**：处理不了或拿不准的单独列出，不硬套。
5. **整体 QA**：重复 G3 的验收清单，覆盖每种模板。
6. **线上验收**（用户发布后）：各类页面返回 200、无报错、追踪事件不重复、手机端加购到结账跑通。
7. **交接文档**：做了什么、数量、备份位置、怎么在后台自己改、用户待办、待确认问题清单。

提醒用户：从复制主题到发布期间，对线上主题的改动会在发布后丢失，这段时间尽量别动线上主题。

## 可选阶段：产品内容迁移与文案重写

用户要求重写产品描述、统一术语或整理产品页内容时启用。它和页面设计并行走同一套闸门："立标准"在 G1 前后完成，3 个试点产品就是 G3 的样板产品页，批量重写在 G4 定稿后和页面铺开一起做。完整做法见 `references/content-rewrite.md`。

## 每道闸门的汇报格式

保持短：
- 这一步完成了什么（数量）
- 链接（预览、Artifact、文档）
- 需要用户决定的问题（给选项）
- 下一步是什么，等确认后开始

## 规则

- **没有用户明确确认，不过闸门。** 试点 / 样板做完必须停下等确认，再批量。
- **不发布、不改线上。** 发布主题、上线站点、打开 app 嵌入都由用户自己做。
- **不输入密码。** 需要登录后台时由用户自己在浏览器里登录。
- **不编造**评价、认证、数字、背书和故事；查不到就标【待用户补充】。
- **改前备份、改后回读**，以系统里读回来的数据为准，不以接口返回为准。
- **范围外的问题只列清单**，交给用户决定。

## 在 Claude 之外运行

这份流程是为 Claude 写的，个别地方提到了 Claude 的工具名。在 ChatGPT、Codex 或其他 Agent 里运行时：
- "AskUserQuestion"：在对话里列出编号选项，让用户回复。
- "Artifact"：用平台的 Canvas 或类似功能；没有就交付自包含的 HTML 文件。
- 连接器 / MCP：用平台已连接的工具或 Actions；没有就用浏览器（用户自己登录）或导出 / 导入文件，并说明哪些步骤需要用户手动完成。
- "项目（Project）"和记忆：把进度文档作为文件交给用户，下次会话开始时让用户贴回来。
